# Deploy InferScale on one Vast.ai server with 4 or 8 RTX 5090s

This walkthrough targets **one physical GPU server**, rented as a full Ubuntu VM
on Vast.ai. Kubernetes calls that server a **node**. A **worker** is one running
copy of a model; **tensor parallelism (TP)** is how many GPUs that copy uses.
A container **image** is a packaged program, a **registry** stores those packages,
and an image **digest** is its immutable fingerprint.

**Current status, September 2026: ready to prepare and qualify the remote host;
not yet a signed-off production-v1 release.** Nine local GPU smoke checks passed,
but the standard pinned Gateway stack does not provide the required inference
integration. The local test used an experimental adapter. That adapter still
cannot implement all the required multi-revision routing. This is software work
that remains, not a missing rental setting. Do not treat deployment of the base
manifests as proof that requests can reach models.

The release owner must resolve the Gateway integration and collect the
[live conformance evidence](../../tests/conformance/gateway/README.md) before
opening customer access. `make release-check` deliberately fails while the lock
file says `pending`. It does not become safe to change that word simply because
Pods are Running. The laptop has demonstrated prefix-cache hits and a cache-warm
scale-from-zero request through Kubernetes, Gateway and EPP. Multi-GPU execution,
healthy canary promotion, burst scale-up and TensorRT-LLM parity still require
their remaining checks; some checks can use local CPU fixtures. See the
[pre-rental validation record](pre-rental-validation.md) for the current evidence.

The steps below distinguish host preparation, isolated qualification, and the
final production gate. They do not purchase a machine, publish images, or change
a remote cluster automatically. Values such as your account, IPs, domain,
passwords, and approved dependency versions must come from your actual setup.
Unless a step explicitly says laptop, run its commands in the same VM terminal.
Keep that session open so the exported settings remain available between steps.

1. **Choose how to use the GPUs.**

   You can use all eight cards without asking one worker to use eight cards.
   InferScale v1 accepts TP1, TP2, and TP4. TP8 remains outside the agreed API and
   has not been enabled in this change.

   | GPUs in server | GPUs per worker | Maximum workers if all cards are occupied | Workers to reserve for an overlapping replacement |
   |---|---:|---:|---:|
   | 4 | 1 | 4 | At least 1 |
   | 4 | 2 | 2 | At least 1 |
   | 4 | 4 | 1 | Cannot overlap; another 4 GPUs would be needed |
   | 8 | 1 | 8 | At least 1 |
   | 8 | 2 | 4 | At least 1 |
   | 8 | 4 | 2 | At least 1 |

   Those are GPU capacity limits, not throughput promises. For the first Qwen3-8B
   deployment, start with one TP1 worker, then measure additional independent
   workers. A 5090 has 32 GB of VRAM, compute capability 12.0, and no NVLink;
   communication between cards can make TP slower than additional independent
   workers for a model that fits on one card. Measure both layouts. Eight cards
   do not automatically act like one 256 GB card.
   [NVIDIA specifications](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5090/)

2. **Prepare accounts and the release information before renting.**

   Have a Vast.ai account with billing enabled, an SSH public key, a domain you
   control, and a registry account that can store the InferScale images. Upload
   only the public SSH key, the file ending in `.pub`. Keep its private partner
   on your computer. The [Vast SSH guide](https://docs.vast.ai/documentation/instances/connect/ssh)
   explains how to create a key if you do not have one.

   The release owner must supply the compatible Gateway matrix, the exact
   Kubernetes version and installer checksum, and explicit NVIDIA device-plugin
   and DCGM chart versions. The project locks application dependencies in
   `versions.lock.yaml`; GPU chart versions and the k3s installer checksum are
   still operator inputs. Do not substitute `latest` for unresolved inputs.

   For customer service, arrange PostgreSQL and a **single-primary, non-sharded
   Valkey/Redis-compatible endpoint**, with backups, authentication, TLS, and a
   tested private network/VPN connection from the VM. InferScale does not
   configure managed databases, VPNs, Redis Cluster, or Sentinel itself. The
   default bundled databases are useful for isolated qualification but are not
   a durable production database service.

3. **Rent the right kind of Vast instance.**

   In Vast, choose the **Ubuntu 22.04 VM** template, then filter for RTX 5090
   and a single offer containing 4 or 8 GPUs. Confirm VM support
   (`vms_enabled=true`), the full GPU allocation, available disk, CPU/RAM, rental
   duration, and price before renting. Prefer a non-interruptible offer for a
   service. Availability and prices must be checked when renting.

   Do not choose the ordinary PyTorch/Jupyter Docker template for this guide.
   The VM must have `systemd`, root/sudo access, nested container support, and all
   rented GPUs visible. Vast documents these VM capabilities and notes that SSH
   keys must be added before VM creation.
   [Vast VM instructions](https://docs.vast.ai/guides/instances/virtual-machines)

   As a planning starting point, allow 128 GiB host RAM for four cards or 256 GiB
   for eight, at least 16 CPU threads, and roughly 500 GB of fast SSD space.
   These are allowances for this stack, builds, and Qwen3-8B qualification, not
   measured minimums. Larger models, concurrent engine builds, and retained
   model revisions need more. Check the VM's actual allocated resources rather
   than assuming it receives everything advertised for the physical machine.

   Configure inbound SSH and a TCP mapping to VM port 443. Vast may assign a
   different external port. Record both the public IP and external HTTPS port;
   request a stable assignment. Do not open Kubernetes 6443, PostgreSQL 5432,
   Valkey 6379, model 8000, or Grafana to the Internet. During qualification,
   restrict HTTPS to the test clients where the provider/network permits it.

4. **Connect and copy the current source, including uncommitted fixes.**

   Open the Vast instance's Connect panel and copy its SSH command. Run that in
   your laptop's terminal. The prompt is now on the rented VM; commands there
   consume the VM's resources, not the laptop's.

   Use a source archive of the current workspace, not `git clone` of the old
   commit: these changes have intentionally not been committed or pushed.
   On the laptop, from the repository, create a source-only archive:

   ```bash
   python3 - <<'PY'
   import subprocess, tarfile
   from pathlib import Path
   paths = subprocess.check_output(['git', 'ls-files', '-z', '--cached', '--others', '--exclude-standard']).split(b'\0')
   with tarfile.open('/tmp/inferscale-source.tar.gz', 'w:gz') as archive:
       for raw in paths:
           if raw:
               path = Path(raw.decode())
               if path.is_file():
                   archive.add(path, arcname=str(path), recursive=False)
   PY
   sha256sum /tmp/inferscale-source.tar.gz
   git rev-parse HEAD
   ```

   Review that only intended source files are included. Transfer that archive
   using `scp -P SSH_PORT /tmp/inferscale-source.tar.gz USER@HOST:~/`, substituting
   the user, host, and port from Vast's SSH command. Keep the archive checksum and
   parent commit with the release record. The checksum identifies this working
   tree; the parent commit alone does not identify uncommitted changes.

   On the VM:

   ```bash
   mkdir -p ~/InferScale
   tar -xzf ~/inferscale-source.tar.gz -C ~/InferScale
   cd ~/InferScale
   sudo apt-get update
   sudo apt-get install -y ca-certificates curl python3 python3-yaml jq tmux
   nvidia-smi --query-gpu=index,name,memory.total,driver_version --format=csv
   nvidia-smi topo -m
   systemctl --version
   command -v nvidia-container-runtime
   docker version
   free -h
   df -h /
   ```

   Expect exactly the rented number of RTX 5090s, about 32 GB each, and working
   Docker/systemd. If devices or the NVIDIA container runtime are missing, fix
   the VM image before continuing. Install the toolkit using NVIDIA's
   [container toolkit instructions](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html).
   Keep one tested driver/toolkit combination. Do not copy the laptop's Windows
   driver or assume its version applies to Linux.

5. **Install Kubernetes and expose the GPUs to it.**

   On the VM, set `GPU_COUNT` to 4 or 8. Fill the approved checksum and chart
   versions supplied in step 2. Install a verified Helm binary if `helm version`
   does not work. Follow the [Helm installation instructions](https://helm.sh/docs/intro/install/).

   ```bash
   export GPU_COUNT=8
   export INFERSCALE_NODE_NAME=inferscale-gpu-01
   export K3S_VERSION=v1.36.2+k3s1
   export K3S_INSTALLER_SHA256=REPLACE_WITH_APPROVED_64_CHARACTER_CHECKSUM
   sudo env K3S_VERSION="$K3S_VERSION" \
     K3S_INSTALLER_SHA256="$K3S_INSTALLER_SHA256" \
     INFERSCALE_EXPECTED_GPU_COUNT="$GPU_COUNT" \
     INFERSCALE_NODE_NAME="$INFERSCALE_NODE_NAME" \
     INFERSCALE_GPU_SKU=RTX_5090 scripts/bootstrap-gpu-host.sh
   mkdir -p ~/.kube
   sudo install -o "$(id -u)" -g "$(id -g)" -m 600 \
     /etc/rancher/k3s/k3s.yaml ~/.kube/inferscale-vast.yaml
   export KUBECONFIG="$HOME/.kube/inferscale-vast.yaml"
   export NVIDIA_DEVICE_PLUGIN_CHART_VERSION=REPLACE_WITH_APPROVED_VERSION
   export DCGM_EXPORTER_CHART_VERSION=REPLACE_WITH_APPROVED_VERSION
   scripts/install-gpu-components.sh
   scripts/verify-remote-gpu.sh "$GPU_COUNT" --node "$INFERSCALE_NODE_NAME"
   ```

   Run `kubectl` inside the VM so the kubeconfig's loopback address is correct.
   The script selects NVIDIA's container runtime, labels only this node, and
   creates cache directories writable by the model-fetch process. The plugin
   exposes exclusive GPUs; time slicing and MIG are not used. GPU monitoring
   gets its own privileged namespace; application monitoring stays restricted.
   [K3s NVIDIA runtime documentation](https://docs.k3s.io/advanced#nvidia-container-runtime)

   The last command must report the exact physical and Kubernetes GPU count,
   the expected product, and a Ready, schedulable node. Record the value of its
   `kubernetes.io/hostname` label; that is what the model cache must be pinned to.

6. **Build the current images on the VM or a dedicated build machine.**

   Use `tmux new -s inferscale-build` so an SSH disconnect does not kill a build.
   Build one image at a time. The supplied release build script is sequential;
   do not run it in several terminals. GPU runtime images are large downloads.
   The vLLM Dockerfile adds the corrected entrypoint to an upstream binary image;
   no ConfigMap replacement of that entrypoint should be needed remotely.

   Set `REGISTRY` to your writable repository prefix, for example
   `ghcr.io/YOUR_ACCOUNT/inferscale`, then log in with `docker login ghcr.io`.
   Use an equivalent login if you chose another registry. Keep the application
   images readable by this cluster. For a private registry, arrange pull Secrets
   as described below before creating workers.

   ```bash
   export REGISTRY=ghcr.io/REPLACE_WITH_ACCOUNT/inferscale
   export TAG=v1-5090-candidate
   export INFERSCALE_GIT_COMMIT=REPLACE_WITH_PARENT_COMMIT_FROM_STEP_4
   export PYTHON_BASE_IMAGE="python:3.11.13-slim-bookworm@$(python3 -c 'import yaml; print(yaml.safe_load(open("versions.lock.yaml"))["python"]["modelcacheBaseDigest"])')"
   export GO_BASE_IMAGE="golang:1.26.5-alpine@$(python3 -c 'import yaml; print(yaml.safe_load(open("versions.lock.yaml"))["go"]["buildImageDigest"])')"
   export DISTROLESS_BASE_IMAGE="gcr.io/distroless/static-debian12:nonroot@$(python3 -c 'import yaml; print(yaml.safe_load(open("versions.lock.yaml"))["go"]["runtimeImageDigest"])')"
   export API_IMAGE="$REGISTRY/api:$TAG"
   export CONTROLLER_IMAGE="$REGISTRY/controller:$TAG"
   export ADMISSION_IMAGE="$REGISTRY/admission:$TAG"
   export MIGRATE_IMAGE="$REGISTRY/migrate:$TAG"
   export MODEL_CACHE_IMAGE="$REGISTRY/modelcache:$TAG"
   export BENCHMARK_IMAGE="$REGISTRY/benchmark:$TAG"
   export VLLM_IMAGE="$REGISTRY/vllm:$TAG"
   export TRTLLM_IMAGE="$REGISTRY/trtllm:$TAG"
   scripts/build-release-images.sh
   for variable in API_IMAGE CONTROLLER_IMAGE ADMISSION_IMAGE MIGRATE_IMAGE MODEL_CACHE_IMAGE BENCHMARK_IMAGE VLLM_IMAGE TRTLLM_IMAGE; do
     docker push "${!variable}"
     digest_ref=$(docker image inspect --format '{{index .RepoDigests 0}}' "${!variable}")
     export "$variable=$digest_ref"
   done
   ```

   This is a qualification build from the recorded source snapshot, not a claim
   that the parent commit includes the new changes. Retain the source archive,
   checksum, build output, and digest references. For the eventual approved
   release, the release owner should establish the final source identity. These
   instructions do not commit your workspace.

   The full build includes the TensorRT wrapper because existing manifests
   reference its image even while the feature is disabled. It does not establish
   TensorRT compatibility. Keep its feature gate off until separately tested.

7. **Check real CUDA execution before loading a model.**

   Do this on the idle VM before deploying InferScale workers. The test imports
   the newly built vLLM image, checks device capability, and performs a tiny GPU
   operation on every visible card. It does not allocate model weights.

   ```bash
   docker run --rm --gpus all --memory=4g --cpus=2 \
     --entrypoint python3 "$VLLM_IMAGE" -c '
   import torch
   print("PyTorch", torch.__version__, "CUDA", torch.version.cuda)
   assert torch.cuda.is_available()
   for i in range(torch.cuda.device_count()):
       print(i, torch.cuda.get_device_name(i), torch.cuda.get_device_capability(i))
       x = torch.ones((64, 64), device=f"cuda:{i}")
       assert (x @ x).sum().item() == 64**3
       torch.cuda.synchronize(i)
   print("CUDA arithmetic passed on", torch.cuda.device_count(), "GPUs")'
   ```

   Expect the chosen count and `(12, 0)` for every RTX 5090. A host `nvidia-smi`
   success alone is insufficient. Repeat actual inference using TP1, TP2, and
   TP4 inside Kubernetes during step 12; the small test does not verify GPU
   collectives or serving. NVIDIA's advertised CUDA version in `nvidia-smi` is
   driver compatibility, not the CUDA toolkit version inside the container.
   Record both. [vLLM installation guidance](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/)

8. **Prepare the domain, TLS, storage credentials, and monitoring login.**

   At your DNS provider, point a hostname such as `inference.example.com` at the
   recorded Vast public IP. If Vast mapped VM 443 to external port 40123, your
   public origin is `https://inference.example.com:40123`. Otherwise use standard
   `https://inference.example.com`. DNS alone does not configure the port mapping.

   Obtain a certificate for that hostname through your certificate provider or
   DNS-based ACME process. Use the full certificate chain and its private key.
   Arrange automatic renewal and replacement of the Kubernetes Secret before
   expiry. The repository's helper installs a certificate; it does not issue or
   renew one. Do not use `curl -k` to make a broken certificate look valid.

   ```bash
   kubectl apply -f deploy/base/inferscale/namespace.yaml
   kubectl apply -f deploy/base/monitoring/namespace.yaml
   scripts/create-tls-secret.sh /secure/path/fullchain.pem /secure/path/privkey.pem
   install -d -m 700 "$HOME/inferscale-secrets"
   umask 077
   read -rsp 'PostgreSQL connection URL: ' database_url; echo
   printf %s "$database_url" > "$HOME/inferscale-secrets/database_url"
   unset database_url
   read -rsp 'Valkey rediss connection URL: ' valkey_url; echo
   printf %s "$valkey_url" > "$HOME/inferscale-secrets/valkey_url"
   unset valkey_url
   python3 -c 'import secrets; print(secrets.token_hex(32), end="")' > "$HOME/inferscale-secrets/benchmark_callback_signing_key"
   printf %s "$BENCHMARK_IMAGE" > "$HOME/inferscale-secrets/benchmark_runner_image"
   printf %s "$VLLM_IMAGE" > "$HOME/inferscale-secrets/runtime_vllm_image"
   printf %s "$TRTLLM_IMAGE" > "$HOME/inferscale-secrets/runtime_trtllm_image"
   printf %s "$MODEL_CACHE_IMAGE" > "$HOME/inferscale-secrets/modelcache_image"
   kubectl -n inferscale-system create secret generic inferscale-storage \
     --from-file="$HOME/inferscale-secrets" --dry-run=client -o yaml | kubectl apply -f -
   install -d -m 700 "$HOME/inferscale-grafana"
   printf admin > "$HOME/inferscale-grafana/username"
   read -rsp 'New Grafana password: ' grafana_password; echo
   printf %s "$grafana_password" > "$HOME/inferscale-grafana/password"
   unset grafana_password
   kubectl -n inferscale-monitoring create secret generic grafana-admin \
     --from-file="$HOME/inferscale-grafana" --dry-run=client -o yaml | kubectl apply -f -
   ```

   Use a PostgreSQL URI with certificate verification, such as
   `postgresql://USER:PASSWORD@HOST:5432/DATABASE?sslmode=verify-full`, and a Valkey
   URI such as `rediss://USER:PASSWORD@HOST:6379/0`. Percent-encode special
   characters in credentials. The Valkey URL takes precedence over the old
   plaintext `valkey_addr` and verifies certificates with the system trust store;
   URL query parameters that weaken verification are rejected. A private CA
   requires a reviewed CA mounting/trust configuration. Test connectivity from
   the VM first. Managed service firewall rules must allow the VM/VPN source.

   If your image registry is private, create its pull Secret now. Use a token
   with permission to read the images; enter its registry hostname (for example
   `ghcr.io`), username, and token at the prompts. Skip this block for public
   application images.

   ```bash
   read -rp 'Registry hostname: ' REGISTRY_HOST
   read -rp 'Registry username: ' REGISTRY_USERNAME
   read -rsp 'Registry read token: ' REGISTRY_READ_TOKEN; echo
   export REGISTRY_HOST REGISTRY_USERNAME REGISTRY_READ_TOKEN
   python3 - <<'PY'
   import base64, json, os
   from pathlib import Path
   auth = base64.b64encode((os.environ['REGISTRY_USERNAME'] + ':' + os.environ['REGISTRY_READ_TOKEN']).encode()).decode()
   path = Path.home() / 'inferscale-registry.json'
   path.write_text(json.dumps({'auths': {os.environ['REGISTRY_HOST']: {'auth': auth}}}))
   path.chmod(0o600)
   PY
   unset REGISTRY_READ_TOKEN
   export INFERSCALE_IMAGE_PULL_SECRET=inferscale-registry
   kubectl apply -f deploy/base/model-cache/namespace.yaml
   for namespace in inferscale-system inferscale-model-cache; do
     kubectl -n "$namespace" create secret generic "$INFERSCALE_IMAGE_PULL_SECRET" \
       --type=kubernetes.io/dockerconfigjson \
       --from-file=.dockerconfigjson="$HOME/inferscale-registry.json" \
       --dry-run=client -o yaml | kubectl apply -f -
   done
   ```

   The release renderer uses that Secret for control-plane images and configures
   controller-created prefetch, engine, and runtime Pods. Kubernetes Secrets are
   namespace-specific; copying a Secret to the system namespace does not grant
   workers in other namespaces access. Step 11 copies it into the first tenant.
   The sample Qwen model is public. Gated/private Hugging Face models additionally
   require a tenant Secret with key `token`, named by `INFERSCALE_HF_TOKEN_SECRET`.

9. **Render and review the intended deployment before applying it.**

   The main path below uses external PostgreSQL/Valkey. Use their private/VPN
   destination addresses as `/32` IPv4 or `/128` IPv6 CIDRs. This is a precise
   firewall destination, not a password. Obtain the post-translation Kubernetes
   API address from the Endpoints below; k3s commonly uses port 6443. Do not use
   `0.0.0.0/0` or disable NetworkPolicy to get connectivity working.

   ```bash
   kubectl get endpoints kubernetes -n default -o wide
   export INFERSCALE_GPU_NODE_NAME=$(kubectl get node "$INFERSCALE_NODE_NAME" -o jsonpath='{.metadata.labels.kubernetes\.io/hostname}')
   export PUBLIC_BASE_URL=https://REPLACE_WITH_YOUR_HOSTNAME_AND_OPTIONAL_PORT
   export INFERSCALE_BENCHMARK_PROVIDER=vast
   export INFERSCALE_BENCHMARK_INFERENCE_BASE_URL="$PUBLIC_BASE_URL"
   export INFERSCALE_BENCHMARK_PROMETHEUS_URL=http://prometheus.inferscale-monitoring.svc.cluster.local:9090
   export INFERSCALE_BENCHMARK_DRIVER_VERSION=REPLACE_WITH_OBSERVED_DRIVER_VERSION
   export INFERSCALE_BENCHMARK_CUDA_VERSION=REPLACE_WITH_RECORDED_CUDA_VERSION
   export REMOTE_EXTERNAL_STORAGE=true
   export CLUSTER_POSTGRES_CIDRS='["REPLACE_WITH_PRIVATE_DATABASE_IP/32"]'
   export CLUSTER_VALKEY_CIDRS='["REPLACE_WITH_PRIVATE_VALKEY_IP/32"]'
   export CLUSTER_KUBERNETES_API_CIDRS='["REPLACE_WITH_PRIVATE_NODE_API_IP/32"]'
   export CLUSTER_POSTGRES_PORT=5432
   export CLUSTER_VALKEY_PORT=6379
   export CLUSTER_KUBERNETES_API_PORT=6443
   scripts/render-remote-release.sh "vast-${GPU_COUNT}x5090" > "$HOME/inferscale-release.yaml"
   ```

   Check that the file contains your hostname, correct node label, immutable
   `@sha256:` images, HTTPS listener, external database egress, and no bundled
   database workloads. There should be no development fake runtime, laptop
   entrypoint ConfigMap, or WSL environment overrides. The renderer requires the
   hostname pin because a successful model download on one disk cannot prove
   another node has the same files.

   Rendering is offline and does not waive release gates. This flag removes
   development storage from a **new manifest**; it does not migrate data or
   delete existing live databases. Do not switch an occupied installation to
   external storage without a separate tested database migration/backup plan.

   For an isolated throwaway qualification only, leave
   `REMOTE_EXTERNAL_STORAGE=false` and use the bundled databases. That alternative
   additionally needs `postgres_user`, `postgres_password`, `postgres_database`,
   the matching internal `database_url`, and `valkey_addr` in the storage Secret.
   Do not carry those development stores into customer service by accident.

10. **Resolve the Gateway dependency and install the qualified candidate.**

    **This step has an unresolved software prerequisite in the current repo.**
    The release owner must supply the tested Gateway/EPP integration, compatible
    CRDs and digest pins, and an installer that actually enables it. Stock pinned
    Envoy Gateway is insufficient. The saved experimental Envoy AI Gateway patch
    fixes duplicate EPP filters, but is not the finished v1 integration. See
    [the experimental adapter record](../../deploy/experimental/envoy-ai-gateway/README.md).

    On the isolated qualification host, after the dependency implementation has
    been corrected, install its exact locked manifests and this release:

    ```bash
    scripts/install-platform-dependencies.sh
    kubectl apply --server-side --field-manager=inferscale-bootstrap -f "$HOME/inferscale-release.yaml"
    kubectl -n inferscale-system wait --for=condition=complete job/inferscale-migrate-000006 --timeout=300s
    kubectl -n inferscale-system rollout status deployment/inferscale-api --timeout=300s
    kubectl -n inferscale-system rollout status deployment/inferscale-controller --timeout=300s
    kubectl -n inferscale-system rollout status deployment/inferscale-admission --timeout=300s
    kubectl -n inferscale-gateway get gateway inferscale
    kubectl -n inferscale-gateway get pods,services
    curl --fail --show-error "$PUBLIC_BASE_URL/healthz"
    ```

    Expect successful database migration, Ready control-plane Pods, and an
    Accepted/Programmed Gateway. A public health response proves reachability,
    not inference routing. Stop and inspect logs if a wait fails; repeatedly
    deleting workloads or rebuilding images will not repair an incompatible
    Gateway. Schema migration Jobs are versioned; upgrading an existing install
    is a separate operation from this fresh-install walkthrough.

11. **Create a tenant and start one small deployment.**

    A tenant groups API keys, quotas, and model deployments. Build the operator
    tool from the same source, then copy its binary out of the build container:

    ```bash
    docker build --build-arg "COMMAND=inferscalectl" -t inferscale-admin:v1-candidate -f build/Dockerfile .
    admin_container=$(docker create inferscale-admin:v1-candidate)
    mkdir -p bin
    docker cp "$admin_container:/usr/local/bin/inferscale" bin/inferscalectl
    docker rm "$admin_container"
    export INFERSCALE_DATABASE_URL=$(cat "$HOME/inferscale-secrets/database_url")
    export INFERSCALE_KUBECONFIG="$KUBECONFIG"
    export INFERSCALE_KUBERNETES_API_CIDRS="$CLUSTER_KUBERNETES_API_CIDRS"
    export INFERSCALE_KUBERNETES_API_PORT="$CLUSTER_KUBERNETES_API_PORT"
    bin/inferscalectl tenant create --slug first-team --name 'First team' \
      --max-deployments 4 --max-gpus "$GPU_COUNT" --requests-per-minute 60 \
      --max-concurrent-requests 4 --max-queued-requests 16 > "$HOME/first-tenant.json"
    export TENANT_ID=$(jq -r '.id' "$HOME/first-tenant.json")
    bin/inferscalectl apikey issue --tenant "$TENANT_ID" --name first-deployment \
      --scope deployments:read,deployments:write,inference > "$HOME/first-key.json"
    export INFERSCALE_API_KEY=$(jq -r '.apiKey' "$HOME/first-key.json")
    unset INFERSCALE_DATABASE_URL
    ```

    Keep the key file private: it is the only retrievable copy of that API key.
    Copy the private registry Secret into the returned tenant namespace now,
    before requesting a model. The default ServiceAccount also needs it for
    scheduled benchmark Jobs. This block is skipped if step 8 used public images:

    ```bash
    export TENANT_NAMESPACE=$(jq -r '.namespace' "$HOME/first-tenant.json")
    if [[ -n "${INFERSCALE_IMAGE_PULL_SECRET:-}" ]]; then
      kubectl -n "$TENANT_NAMESPACE" create secret generic "$INFERSCALE_IMAGE_PULL_SECRET" \
        --type=kubernetes.io/dockerconfigjson \
        --from-file=.dockerconfigjson="$HOME/inferscale-registry.json" \
        --dry-run=client -o yaml | kubectl apply -f -
      kubectl -n "$TENANT_NAMESPACE" patch serviceaccount default --type=merge \
        -p '{"imagePullSecrets":[{"name":"inferscale-registry"}]}'
    fi
    ```

    Add any required Hugging Face Secret there too. The operator tool applies the
    precise Kubernetes API egress rule so EPP can watch endpoints on k3s.

    ```bash
    curl --fail-with-body --show-error "$PUBLIC_BASE_URL/v1/deployments" \
      -H "Authorization: Bearer $INFERSCALE_API_KEY" \
      -H 'Content-Type: application/json' -H 'Idempotency-Key: first-qwen3-8b' \
    ```

12. **Qualify scaling, replacement, and failure behavior before customer traffic.**

    Use the [remote benchmark runbook](../benchmarks/remote-runbook.md) and
    [test strategy](../testing.md). Increase one variable at a time; submit
    changes through the management API with its current ETag/`If-Match`, not
    `kubectl scale` on generated workers. KEDA/controller reconciliation can
    overwrite direct scaling. A rollout is not healthy merely because its
    candidate is deliberately left unschedulable.

    | Qualification | Required observation |
    |---|---|
    | TP1, TP2, TP4 | Actual inference and streaming in each layout; no CUDA/NCCL/worker crashes |
    | Replica scaling | More than one Ready worker, traffic reaches each, and scale-up/down preserves service |
    | Prefix cache on/off | Correct outputs, actual cache-hit evidence, repeated-prefix measurements, correct cache-aware routing |
    | GPU resource accounting | Each worker has exclusive GPU requests equal to TP; no accidental time slicing or oversubscription |
    | Cache states | Fresh cold download, verified warm disk cache, warm process; corruption and disk-full behavior |
    | Two tenants under load | Quotas, fairness, backpressure, header-spoofing rejection, and isolation |
    | Healthy replacement | Stable and Ready candidate overlap, accurate canary weights, shadowing, promotion, rollback |
    | Faults and recovery | Worker crash/OOM, EPP restart, Valkey outage, unavailable telemetry, controller restart |
    | Operations | PostgreSQL backup restored on a disposable instance; TLS renewal and key rotation exercised |
    | TensorRT/auto selection | Real engine build on this GPU architecture and parity/benchmark evidence before enabling either feature |

    The shared-memory mount added for worker communication is bounded at 2 GiB
    host RAM per allocated GPU (TP4: 8 GiB). It is allocated as used, not reserved
    up front. Watch total host memory, disk, GPU utilization, thermals, and errors
    during the test. Unsupported consumer-GPU telemetry fields must be recorded
    as unavailable rather than reported as zeros.

    Keep scale-to-zero, progressive rollout, TensorRT-LLM, and automatic backend
    selection off for the first basic deployment. Enable and validate each
    promised feature in isolation before calling the complete v1 finished.
    Save raw results, source/image identities, exact hardware/driver/container
    versions, and observed rental cost. The full procedure and passing evidence
    must match the exact final lock file:

    ```bash
    make release-check
    ```

    Run that command in the release/test environment with the documented Go and
    Python dependencies installed. Until it passes and remote behavior is
    accepted, keep this an isolated qualification service. The current lock
    file intentionally prevents a production sign-off.

13. **Open access, monitor, and plan recovery.**

    After sign-off, grant customers limited tenant keys, raise quotas gradually,
    and reserve enough physical cards for the maximum simultaneous stable and
    candidate workers. The formula is **workers × GPUs per worker**, plus other
    tenants and active engine builds. Kubernetes quotas permit controlled surge;
    they cannot create physical GPUs that the rental does not contain.

    View Grafana through a local-only port forward on the VM, carried through
    an SSH tunnel from your laptop:

    ```bash
    kubectl -n inferscale-monitoring port-forward --address 127.0.0.1 svc/grafana 3000:3000
    ```

    In a second laptop terminal, use the Vast SSH command with
    `-L 3000:127.0.0.1:3000`, then open `http://localhost:3000` and use the login
    from step 8. Confirm Prometheus actually sees DCGM and runtime/EPP metrics.
    Configure alert delivery to an operator; the checked-in dashboards and rules
    alone do not notify anyone. Monitoring data currently uses ephemeral storage;
    add durable metrics/log storage or export it if retention across recreation
    is required.

    A single physical host is one failure domain, even with eight GPUs and two
    API replicas. A host loss interrupts all inference. Store backups, source,
    release manifests, TLS material, and credentials outside the rental; test
    rebuilding a replacement host and restoring database state. Model weights
    can be downloaded again. Do not delete occupied model-cache directories.

    To retire the rental, stop new traffic, let requests drain, export results
    and backups, then use Vast's instance controls to terminate the intended
    instance. Confirm its billing/storage state in Vast. Stopping model Pods
    alone does not terminate the rented server or its charges.
