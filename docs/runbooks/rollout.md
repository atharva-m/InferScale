# Runbook: progressive rollout

Promotion requires candidate readiness, fresh Prometheus data, minimum samples, dwell time, and passing error/TTFT/TPOT/queue/OOM/restart gates. A missing signal pauses; it never counts as success.

Shadow is a distinct telemetry path: Gateway API mirrors directly to the candidate runtime Service and discards the response, so the candidate EPP does not see those requests. During Shadow the controller counts completed `inferscale_shadow_runtime_requests_total` requests over the entire stage and evaluates runtime error/TTFT/TPOT plus direct pod OOM/restart and DCGM XID safety. EPP queue and comparative EPP gates begin at Canary5. The pinned vLLM runtime exposes this shadow contract; a runtime without all of those signals pauses promotion closed. An automatic insufficient-traffic pause preserves `status.rollout.stageStartedAt`, while resuming an operator pause starts a new dwell/sample window.

On regression, verify Gateway has a stable-only backend set, then inspect `status.rollout.lastRollback`. It contains only a bounded source/stage/window, request count, rates in parts per million, rounded millisecond percentiles, and aggregate safety counts—never PromQL, pod names, request IDs, or arbitrary labels. The same snapshot is copied into PostgreSQL `rollout_history.details`. The failed runtime and EPP Deployments are scaled to zero and retained with retirement annotations for 24 hours; subsequent reconciliation does not restore or wait for them. Database evidence remains after Kubernetes resources are pruned. Shadow output must never reach the client and shadow usage must be billed to platform rollout cost, not tenant output tokens.

If controller restart leaves desired/observed route weights different, do not manually promote. Reconciliation restores the persisted safe stage or rolls back. A manual abort follows the same durable transition and traffic verification path as an automatic rollback.

Rollback saves the failure before changing the route. Candidate workers stop only after the Gateway accepts the current stable-only route generation; unfinished candidate build jobs are suspended. A replacement desired revision also retires superseded runtime/EPP deployments and removes their autoscalers, even when the candidate pointer has already advanced. Promotion saves the new stable identity before retiring the previous stable resources, so cleanup resumes safely after a restart.
